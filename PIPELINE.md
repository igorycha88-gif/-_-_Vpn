# SmartTraffic — Конвейер разработки (Development Pipeline)

> Конвейер определяет обязательный порядок прохождения задач через роли с чёткими правилами передачи,
> автоматическими хардгейтами, TDD-first подходом и эскалацией к пользователю.

## Фундаментальные правила (НЕЛЬЗЯ НАРУШАТЬ)

### Правило 1: Конвейер запускается ВСЕГДА

Любая задача от пользователя — фича, баг-фикс, рефакторинг, вопрос — проходит конвейер.
Исключений нет.

### Правило 2: Этапы НЕЛЬЗЯ пропускать

```
Аналитик → [Архитектор] → Разработчик → Тестировщик → [цикл баг-фикс] → DevOps
```

- Архитектор подключается **ТОЛЬКО** для средних и сложных задач
- Цикл баг-фикс повторяется пока все баги не закрыты
- DevOps получает задачу **ТОЛЬКО** после успешного тестирования

### Правило 3: Хардгейты на каждой передаче

Передача задачи между ролями **БЛОКИРУЕТСЯ** если:
- `make verify` падает — 0 ошибок, 0 failing тестов, покрытие ≥ 80%
- Любой чеклист передачи не пройден
- Тесты не написаны или не покрывают новый код

**Непрохождение хардгейта = ОСТАНОВКА + сообщение пользователю.**

### Правило 4: TDD-first (тесты ДО кода)

Для **ВСЕГО** нового функционала:
1. Сначала пишется тест, который падает (RED)
2. Потом пишется минимальный код, чтобы тест прошёл (GREEN)
3. Потом рефакторинг при необходимости (REFACTOR)
4. `make verify` — все проверки зелёные

Для **баг-фиксов**:
1. Сначала пишется failing test, воспроизводящий баг (RED)
2. Баг фиксится минимальным изменением (GREEN)
3. `make verify` — все проверки зелёные

### Правило 5: Эскалация к пользователю (ОБЯЗАТЕЛЬНА)

**ОСТАНОВИТЬСЯ и спросить пользователя** если:
- Что-то не получается на любом этапе конвейера
- Нужно отклониться от требований конвейера
- Требования противоречивы или неполны
- Есть несколько вариантов решения с разными компромиссами
- Хардгейт не проходит и причина неясна
- Требуется удалить или изменить тесты, которые были написаны ранее
- Затронуты секреты, ключи, продакшен-конфигурация
- Оценка времени/сложности значительно отличается от ожидаемой

**Формат эскалации:**
```
⚠️ ЭСКАЛАЦИЯ К ПОЛЬЗОВАТЕЛЮ

Проблема: [описание]
На этапе: [роль]
Варианты решения:
  1. [вариант 1 + плюсы/минусы]
  2. [вариант 2 + плюсы/минусы]
Жду вашего решения.
```

| Роль | Файл навыков | Назначение |

| **Тестировщик** | `.opencode/skills/tester.md` | Тестирование, валидация, ретест |
| **DevOps** | `.opencode/skills/devops.md` | Сборка, тесты в Docker, развёртывание, итоги |

## Правила маршрутизации задач

### Определение сложности

| Критерий | Простая | Средняя | Сложная |
|---|---|---|---|
| Количество файлов | 1–3 | 4–10 | >10 |
| Новая функциональность | Нет | Частично | Да |
| Затрагивает архитектуру | Нет | Косвенно | Да |
| Требует новый API/эндпоинт | Нет | Возможно | Да |
| Интеграция новых библиотек | Нет | Да | Да |
| Изменение схемы БД | Нет | Возможно | Да |

**Маршрутизация по сложности:**
- **Простая** → Аналитик → Разработчик
- **Средняя** → Аналитик → Архитектор → Разработчик
- **Сложная** → Аналитик → Архитектор → Разработчик

## Хардгейты (автоматические ворота)

### GATE-1: Передача Аналитик → Разработчик / Архитектор

**Автоматическая проверка:**
- [ ] Чтение навыка: `.opencode/skills/analyst.md`
- [ ] Чтение контекста: TZ.md, ARCHITECTURE.md, PIPELINE.md
- [ ] Сложность определена и обоснована
- [ ] Критерии приёмки сформулированы (функциональные + нефункциональные + edge-cases)
- [ ] Для каждого нового функционала указан план тестирования
- [ ] Передача оформлена по шаблону

### GATE-2: Передача Архитектор → Разработчик

**Автоматическая проверка:**
- [ ] Чтение навыка: `.opencode/skills/architect.md`
- [ ] Интерфейсы и контракты описаны
- [ ] Точки внедрения моков определены
- [ ] Обработка ошибок спроектирована
- [ ] Передача оформлена по шаблону

### GATE-3: Передача Разработчик → Тестировщик (КРИТИЧЕСКИЙ)

**Автоматическая проверка (`make verify` — ОБЯЗАТЕЛЬНО):**
- [ ] `go vet ./...` — 0 ошибок
- [ ] `golangci-lint run` — 0 ошибок
- [ ] `go test -race -count=1 -coverprofile=coverage.out ./...` — 0 failing, покрытие нового кода ≥ 80%
- [ ] `go build ./...` — сборка успешна
- [ ] `npm run lint` — 0 ошибок
- [ ] `npm run typecheck` — 0 ошибок
- [ ] `npm run test -- --coverage --passWithNoTests` — 0 failing
- [ ] `npm run build` — сборка успешна
- [ ] TDD соблюдён: тесты написаны ДО реализации
- [ ] Все edge-cases из критериев приёмки покрыты тестами
- [ ] Само-ревью выполнено
- [ ] Передача оформлена по шаблону

**Если любой пункт не пройден — задача НЕ передаётся Тестировщику.**

### GATE-4: Передача Тестировщик → DevOps

**Автоматическая проверка:**
- [ ] Все критерии приёмки подтверждены
- [ ] Нет Critical/Major багов
- [ ] Все автоматические тесты пройдены (`make verify`)
- [ ] Регрессионное тестирование пройдено
- [ ] Отчёт о тестировании оформлен

### GATE-5: DevOps — финальный

**Автоматическая проверка:**
- [ ] `docker compose down` — остановлены
- [ ] `docker compose build --no-cache` — пересобраны без кэша
- [ ] `docker compose up -d` — запущены
- [ ] `docker compose ps` — все контейнеры Up
- [ ] `docker compose logs --tail=100 [service]` — нет ошибок
- [ ] Все тесты пройдены после пересборки
- [ ] API отвечает (health check)
- [ ] Итоговый отчёт оформлен

## Протокол исправления багов (Bug-Fix Protocol)

```
Тестировщик нашёл баг
        │
        ▼
Разработчик получает баг-репорт
        │
        ├── ШАГ 1: Написать failing test (ВОСПРОИЗВЕСТИ баг)
        │     └── Запустить тест → тест ПАДАЕТ (RED)
        │
        ├── ШАГ 2: Минимальное исправление кода
        │     └── Запустить тест → тест ПРОХОДИТ (GREEN)
        │
        ├── ШАГ 3: Полная верификация
        │     ├── make verify — ВСЕ проверки зелёные
        │     ├── Покрытие ≥ 80% для исправленного модуля
        │     └── Регрессия: все остальные тесты тоже проходят
        │
        ▼
Тестировщик получает на ретест
        │
        ├── Подтверждает исправление бага
        ├── Проверяет, что не сломалось другое (регрессия)
        ├── Прогоняет make verify
        │
        ├── Багов нет ──▶ DevOps
        └── Есть баги  ──▶ снова Разработчику (с ШАГА 1)
```

**Правила баг-фикса:**
- НИКОГДА не фиксить баг без написания failing test первым
- Исправление минимально — только то, что нужно для прохождения теста
- После фикса — `make verify` обязателен
- Цикл повторяется пока все баги не закрыты

## Протокол нового функционала (Feature Protocol — TDD)

```
Разработчик получает спецификацию
        │
        ├── ШАГ 1: Понять требования
        │     └── Прочитать критерии приёмки, edge-cases, контракты
        │
        ├── ШАГ 2: Написать тесты (RED)
        │     ├── Тест на happy path → падает (код ещё не написан)
        │     ├── Тесты на ошибки → падают
        │     ├── Тесты на edge-cases → падают
        │     └── Все новые тесты КОМПИЛИРУЮТСЯ, но ПАДАЮТ
        │
        ├── ШАГ 3: Реализовать код (GREEN)
        │     ├── Минимальная реализация для прохождения тестов
        │     ├── Запустить тесты → все проходят
        │     └── Не писать лишний код сверх того, что нужно для тестов
        │
        ├── ШАГ 4: Рефакторинг (REFACTOR)
        │     ├── Улучшить структуру кода
        │     ├── Убедиться что тесты всё ещё проходят
        │     └── Проверить покрытие ≥ 80%
        │
        ├── ШАГ 5: Само-ревью + make verify
        │     ├── Все ошибки обработаны
        │     ├── Нет TODO/FIXME/hack
        │     ├── Линтер и тайпчекер пройдены
        │     ├── Все тесты пройдены
        │     └── Сборка успешна
        │
        ▼
Тестировщик
```

## Обязательные правила для ВСЕХ ролей

1. **Навыки обязательны к исполнению** — каждая роль обязана следовать всем практикам из своего файла навыка
2. **Контекст проекта** — каждая роль обязана прочитать `TZ.md`, `ARCHITECTURE.md` и `PIPELINE.md` перед началом работы
3. **Чистота кода** — никаких комментариев в коде (кроме случаев явного запроса), никаких TODO/FIXME
4. **Язык** — вся коммуникация на русском языке
5. **Верификация** — перед передачей задачи следующей роли, текущая роль обязана запустить `make verify`
6. **Обратная связь** — при обнаружении проблем на любом этапе, задача возвращается на предыдущий этап с описанием проблемы
7. **Идемпотентность** — повторный запуск любого этапа должен приводить к тому же результату
8. **Эскалация** — при любой неопределённости — спросить пользователя
